# `PLAN.md` 写作规则

## 0x01 文档职责

- `PLAN.md` 记录调研结论、对比分析、实现路径、验收标准与实施进展。
- `PLAN.md` 不重写 `README.md` 中已经稳定的需求定义主干。
- 记录视角为架构师视角：主体写当前有效方案，不写实现流水账。

**【CRITICAL（必须执行，不可协商）】先架构、后落点。**

- 读完架构设计后，读者能回答「如何分层 / 对象如何关联 / 边界与不变量是什么」。
- 读完开发方案后，读者能回答从哪些模块或入口开始开发。
- 文档不合格信号：读者只能看到文件改动、类名清单、PR diff 摘要或测试结果，需自行拼出架构关系。

## 0x02 推荐骨架

| 章节 | 应写内容 |
| --- | --- |
| 调研与约束 | 问题背景、约束、关键结论 |
| 架构设计 | 当前有效设计、职责分层、关键决策、风险与不变量 |
| 开发方案 | 代码落点、接口改造、迁移步骤、测试点 |
| 验收与验证 | 验证策略、必测点、回归口径 |
| 实施进展 | 架构设计更新后的阶段结论与验证结果 |

单章篇幅过长时按主题拆分章节：以 `0x03 ~ 0x05 开发方案 —— xxx（改造主题）` 形式分配子章节编号。

风险与约束不独立成章，按性质并入架构设计或开发方案：

- 影响结构与不变量的风险：落在架构设计的关键决策或边界说明。
- 影响落点与执行步骤的风险：落在开发方案对应主题。

## 0x03 架构设计

### a. 先解释结构

架构设计先讲分层、对象关联、边界与不变量。

- 复杂结构必须可复原：涉及继承链、数据流、协议流、状态机、注册表、工厂或多层职责分离时，至少用一种结构载体（Mermaid、文本拓扑或最小结构代码），`Before / After` 仅作辅助。
- 必须重写的信号：一段内容连续列出多个文件或类却未说明关系、方向、边界或不变量。
- 关键决策写得可判定：默认值、唯一键、优先级、兼容策略、迁移策略。
- 类名和文件名只作架构锚点：可以出现但不替代结构解释。

架构设计禁止以下内容：逐文件变更清单、PR diff 摘要、review finding 汇总、CI 与测试结果堆叠、类名 / 函数名 / 配置项等权罗列。

### b. 围绕事实组织条目

「关键决策 / 不变量 / 边界」是描述维度，不是分章模板。

按当期方案的实际事实抽出核心条目：避免凑成并列子章节后内容大量重复。

Bad：按通用三件套强行分章导致内容大量重复。

```md
### c. 关键决策
### d. 不变量
### e. 边界
```

Good：按当期事实抽核心条目（异常收敛 PLAN 示例）。

```md
### b. 三件事

- 异常收敛：存储不可用统一为 `StoreUnavailableError`。
- wrap 机制：`__init_subclass__` 单点注入，覆盖 `__init__` 与 `do()`。
- 识别范围：仅识别 backend 声明的 `base_exceptions`。
```

### c. 案例对比

Bad：直接铺开开发落点导致架构语义缺失。

```md
实现方案：

- `ListResource` 支持 `service_name` 可选。
- `sync_relations` 改成 diff-sync。
- 全局规则下发 `source="*"`.
```

Good：架构设计先讲清查询协议。

```md
## 0x02 架构设计

### d. 查询机制

| 场景 | 请求特征 | 返回语义 |
| --- | --- | --- |
| 服务视角 | 传 `service_name` | 返回最终生效结果 |
| 应用视角 | 不传 `service_name` | 返回配置本身 |
```

## 0x04 开发方案

### a. 协议落点

开发方案沿架构设计展开，回答协议三问：

- **在哪声明**：抽象 / 协议字段在哪个基类或模块定义。
- **上层如何取用**：上层模块通过哪个入口拿到该抽象。
- **如何收敛**：执行期 / 构造期如何统一收敛，避免 wrap 扩散或语义泄漏。

文件级变更并入协议三问：只回答「入口与责任」，不另立"文件落点"章节单独罗列文件清单或代码现状。

文件表稳定字段：`文件 / 场景 / 入口 / 责任 / 测试点`，协议语义和代码步骤分别承载。

### b. 多主题拆分

单章篇幅较长时按主题拆分章节：以 `0x03 ~ 0x05 开发方案 —— xxx（改造主题）` 形式分配子章节编号。

子章节内部按「先结构、再落点、再边界」顺序展开：不堆叠成长列表。

### c. 案例对比

Bad：把开发落点当成方案主体导致协议三问缺失。

```md
开发方案：

- `ListResource` 支持 `service_name` 可选。
- `sync_relations` 改成 diff-sync。
- 全局规则下发 `source="*"`.
```

Good：协议语义和入口责任分层落子（架构设计沉淀语义、开发方案回答责任）。

```md
## 0x03 开发方案

### a. 协议落点

| 文件 | 场景 | 入口 | 责任 |
| --- | --- | --- | --- |
| `service/resources.py` | 查询 | `ListResource` | 接收 `service_name` 决定视角 |
| `models/service.py` | 写入 | `sync_relations` | diff-sync 收敛写入路径 |
```

## 0x05 验收与验证

结论与验收职责分离：

- 架构设计回答「采用什么结构和为什么」。
- 验收回答「如何证明结构成立」。
- 架构设计不重复验收清单。
- 验收章节不重讲方案价值。

验收口径：

- 验收点用可判定的不变量描述：对外语义、字段约束、回归口径。
- 验证策略合并到本节：不另立「测试策略」「建议验证命令」章节。
- 按工程既定的全量测试入口执行：不在文档堆叠具体命令。

## 0x06 实施进展

- 进展用表格记录：建议表头 `时间`、`对应设计片段`、`结论调整概要`、`改动 / 验证`。
- 条目按时间倒序：最新进展放在表格最上方。
- 单条记录只写「阶段性结论 + 关键判定 + 验证依据」。
- 同日未形成新阶段结论时合并条目：保留当日最终有效结论。
- 新进展改变原方案结论时按序更新：先更新架构设计正文，再更新进展表。

### a. 案例对比

Bad：进展只复述同一动作导致阶段结论缺失。

```md
| 时间 | 结论调整概要 |
| --- | --- |
| `2026-04-16 10:00` | 改表格 |
| `2026-04-16 11:00` | 再改表格 |
| `2026-04-16 14:00` | 继续改表格 |
```

Good：阶段结论倒序排列。

```md
| 时间 | 对应设计片段 | 结论调整概要 | 改动 / 验证 |
| --- | --- | --- | --- |
| `2026-05-04 12:00` | `0x03.b` | 已进行源码分析确认方案无歧义：构造期 wrapper 从入参 `backend` 取 `base_exceptions`，与执行期路径分离。 | 已核对 sync / async store 主路径与 redis 异常体系。 |
```

## 0x07 自检口径

`PLAN.md` 写作、润色或评测时直接用本表反向校验：不把知识库样板正文当成写作模板或内容来源。

| 检查点 | 判定方式 | 修正方向 |
| --- | --- | --- |
| 架构可读 | 只读 `0x01` / `0x02` 仍能看出当前方案。 | 看不出则补总思路与关键决策。 |
| 协议落点 | 开发方案是否回答「在哪声明 / 上层如何取用 / 如何收敛」。 | 缺协议三问则回到架构设计补结构关系。<br />不写"文件落点"单独罗列文件清单。 |
| 验收分离 | 验收是否回答「如何证明结构成立」。 | 重讲方案价值则改为不变量、验证方式、回归口径。 |
| 进展精炼 | 进展是否只写阶段结论与验证结果且按时间倒序。 | 复述方案则合并为当日最终结论。<br />顺序倒置则调整为最新置顶。 |
| 反样板 | 文档是否为了像样板而拉长。 | 当前版本已更清晰、更短、更可验证则不再补装饰性章节。 |
