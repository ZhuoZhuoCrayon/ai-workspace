# 方案写作规则

## 0x01 文档职责

- 记录调研结论、对比分析、实现路径、验收标准与实施进展。
- 不重写 `README.md` 中已经稳定的需求定义主干。
- 记录视角为架构师视角：主体写当前有效方案，不写实现流水账。
- 约束实现结构：说明代码应按什么边界、入口和差异表达方式组织，提前排除冗余实现形态。

**【CRITICAL（必须执行，不可协商）】先架构、后落点。**

- 读完架构设计后，读者能回答「如何分层 / 对象如何关联 / 边界与不变量是什么」。
- 读完开发方案后，读者能回答从哪些模块或入口开始开发。
- 文档不合格信号：读者只能看到文件改动、类名清单、PR 差异摘要或测试结果，需自行拼出架构关系。

## 0x02 推荐骨架

| 章节 | 应写内容 |
| --- | --- |
| 调研与约束 | 问题背景、约束、关键结论 |
| 架构设计 | 当前有效设计、职责分层、关键决策、风险与不变量 |
| 开发方案 | 代码落点、接口改造、迁移步骤、实现结构约束 |
| 验收与验证 | 验证策略、必测点、回归口径 |
| 实施进展 | 架构设计更新后的阶段结论与验证结果 |

单章篇幅过长时按主题拆分章节：以 `0x03 ~ 0x05 开发方案 —— xxx（改造主题）` 形式分配子章节编号。

风险与约束不独立成章，按性质并入架构设计或开发方案：

- 影响结构与不变量的风险：落在架构设计的关键决策或边界说明。
- 影响落点与执行步骤的风险：落在开发方案对应主题。

## 0x03 架构设计

### a. 先解释结构

架构设计先讲分层、对象关联、边界与不变量。

- 复杂结构必须可复原，涉及继承链、数据流、协议流、状态机、注册表、工厂或多层职责分离时，用 Mermaid、文本拓扑或最小结构代码表达关系。
- `Before / After` 只作辅助，不替代结构关系。
- 必须重写的信号：一段内容连续列出多个文件或类却未说明关系、方向、边界或不变量。
- 关键决策写得可判定：默认值、唯一键、优先级、兼容策略、迁移策略。
- 类名和文件名只作架构锚点：可以出现但不替代结构解释。

架构设计禁止以下内容：逐文件变更清单、PR 差异摘要、代码评审问题汇总、持续集成结果堆叠、类名 / 函数名 / 配置项等权罗列。

### b. 围绕事实组织条目

「关键决策 / 不变量 / 边界」是描述维度，不是分章模板。

从当前方案事实抽出核心条目：避免凑成并列子章节后内容大量重复。

Bad：按通用三件套强行分章导致内容大量重复。

```md
### c. 关键决策

### d. 不变量

### e. 边界
```

Good：按当期事实抽核心条目。

```md
### b. 当前有效方案

- 异常收敛：存储不可用统一为 `StoreUnavailableError`。
- 异常族声明：后端声明可包装的基础异常族。
- 单一机制：共享注入机制读取各类声明的方法名集合。
- 收敛边界：选择调用方可感知的唯一上游入口。
- 透传边界：上层只透传统一异常，不捕获底层实现异常。
```

### c. 案例对比

Bad：直接铺开开发落点导致架构语义缺失。

```md
实现方案：

- `service_name` 改成可选。
- 同步逻辑改成差异写入。
- 默认规则下发 `source="*"`.
```

Good：架构设计先讲清查询协议。

```md
## 0x02 架构设计

### d. 查询机制

| 场景 | 请求特征 | 返回语义 |
| --- | --- | --- |
| 服务视角 | 传 `service_name` | 返回最终生效结果 |
| 应用视角 | 不传 `service_name` | 返回配置本身 |
```

## 0x04 开发方案

### a. 协议落点

开发方案沿架构设计展开，回答协议三问。

| 问题 | 写作要求 |
| --- | --- |
| 在哪声明 | 抽象、协议字段或能力开关在哪个基类、接口或模块定义。 |
| 上层如何取用 | 上层模块通过哪个入口拿到该抽象。 |
| 如何收敛 | 执行期、构造期或写入期如何统一收敛，避免逻辑扩散或语义泄漏。 |

文件级变更并入协议三问：只回答「入口与处理方式」，不另立「文件落点」章节单独罗列文件清单或代码现状。

文件表只在能降低理解成本时使用，字段按当前方案选择。

常见字段包括 `文件`、`场景`、`入口`、`处理方式`、`影响范围`。

测试相关内容优先放在验收章节。

### b. 实现结构约束

开发方案必须说明实现结构约束，避免只写文件落点。

| 维度 | 应写内容 | 避免写法 |
| --- | --- | --- |
| 责任边界 | 哪一层、对象或流程拥有该语义，哪些只消费结果。 | 按现象发生点逐点补丁。 |
| 收敛入口 | 多个触发点最终在哪个稳定入口统一处理。 | 在多个生命周期或流程节点重复处理。 |
| 差异表达方式 | 差异通过字段、配置、接口、策略表或能力声明表达。 | 按对象、角色或场景扩多套并列逻辑。 |
| 复用与分叉 | 多端、多模式、多后端或多角色流程如何共享规则，哪些地方允许分叉。 | 语义一致时复制多套落点。 |
| 禁止形态 | 明确禁止会导致重复、跨层泄漏或绕过边界的实现形态。 | 只写正向任务清单。 |

出现以下信号时，必须回到架构边界重新审视：

- 同一职责出现多组并列处理逻辑或辅助函数。
- 多端、多模式、多后端或多角色流程出现复制的入口或流程节点。
- 同一字段清单、状态表、权限规则或错误处理规则在多个位置重复维护。
- 某个内部生命周期被特殊处理，但已有更稳定的上游入口能统一承担该语义。
- 上层验证为了触发异常或状态变化，直接操作下层实现细节。

### c. 多主题拆分

单章篇幅较长时按主题拆分章节：以 `0x03 ~ 0x05 开发方案 —— xxx（改造主题）` 形式分配子章节编号。

子章节内部按「先结构、再落点、再边界」顺序展开：不堆叠成长列表。

### d. 案例对比

Bad：把开发落点当成方案主体导致协议三问和结构约束缺失。

```md
开发方案：

- Web 页面加开关判断。
- API 接口也加开关判断。
- 后台任务也加开关判断。
- 给所有入口补测试。
```

Good：先说明入口责任，再约束实现形态。

```md
### a. 协议落点

| 文件 | 场景 | 入口 | 处理方式 |
| --- | --- | --- | --- |
| `policy/access.py` | 规则判断 | `ActionPolicy` | 统一判断动作是否允许执行。 |
| `api/action.py` | API 入口 | `ActionPolicy.check()` | 只消费策略结果并返回响应。 |
| `tasks/action.py` | 后台任务 | `ActionPolicy.check()` | 只消费策略结果并决定是否执行。 |

### b. 实现结构约束

- 动作可执行规则只在策略层解释。
- Web、API 与后台任务不重复判断字段组合。
- 角色差异通过策略表声明。
- 入口只消费策略结果，不直接读取底层字段。
```

## 0x05 验收与验证

验收与验证只证明方案成立，不展开测试实现设计。

- 验收点用可判定的不变量描述：对外语义、字段约束、关键边界、回归口径。
- 验证策略合并到本节：不另立「测试策略」「建议验证命令」章节。
- 涉及替代真实依赖的测试对象时，只说明它对应哪一层直接依赖。
- 按工程既定的全量测试入口执行：不在文档堆叠具体命令。

## 0x06 实施进展

- 进展用表格记录：建议表头 `时间`、`对应设计片段`、`结论调整概要`、`改动 / 验证`。
- 条目按时间倒序：最新进展放在表格最上方。
- 单条记录只写「阶段性结论 + 关键判定 + 验证依据」。
- 同日未形成新阶段结论时合并条目：保留当日最终有效结论。
- 新进展改变原方案结论时按序更新：先更新架构设计正文，再更新进展表。

Bad：进展只复述同一动作导致阶段结论缺失。

```md
| 时间 | 结论调整概要 |
| --- | --- |
| `2026-04-16 10:00` | 改表格 |
| `2026-04-16 11:00` | 再改表格 |
| `2026-04-16 14:00` | 继续改表格 |
```

Good：阶段结论倒序排列。

```md
| 时间 | 对应设计片段 | 结论调整概要 | 改动 / 验证 |
| --- | --- | --- | --- |
| `2026-05-04 12:00` | `0x03.b` | 已确认动作可执行规则由策略层统一收敛，不在各入口重复判断。 | 已核对 Web、API 与后台任务主路径。 |
```

## 0x07 自检口径

写作、润色或评测时直接用本表反向校验：不把知识库样板正文当成写作模板或内容来源。

| 检查点 | 判定方式 | 修正方向 |
| --- | --- | --- |
| 架构可读 | 只读 `0x01` / `0x02` 仍能看出当前方案。 | 看不出则补总思路与关键决策。 |
| 协议落点 | 开发方案是否回答「在哪声明 / 上层如何取用 / 如何收敛」。 | 缺协议三问则回到架构设计补结构关系。<br />不写「文件落点」单独罗列文件清单。 |
| 实现结构 | 开发方案是否说明责任边界、收敛入口和差异表达方式。 | 缺失则补责任边界、收敛入口、差异表达方式和禁止形态。 |
| 差异表达 | 差异是否通过字段、配置、接口、策略表或能力声明表达。 | 出现多套并列逻辑、重复清单或复制流程时回到架构设计。 |
| 复用分叉 | 多端、多模式、多后端或多角色流程是否说明共享规则与分叉原因。 | 语义一致却复制落点时补共享层说明。 |
| 验收分离 | 验收是否回答「如何证明结构成立」。 | 重讲方案价值则改为不变量、验证方式、回归口径。 |
| 验收克制 | 验收是否只保留证明方案成立所需内容。 | 过细则保留不变量、验证方式和回归口径。 |
| 进展精炼 | 进展是否只写阶段结论与验证结果且按时间倒序。 | 复述方案则合并为当日最终结论。<br />顺序倒置则调整为最新置顶。 |
| 反样板 | 文档是否为了像样板而拉长。 | 当前版本已更清晰、更短、更可验证则不再补装饰性章节。 |
