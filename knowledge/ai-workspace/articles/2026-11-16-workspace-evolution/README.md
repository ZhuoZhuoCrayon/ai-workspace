# AI 工作区半年架构复盘

这套工作区保留短入口、按需 Skill、多仓注册表和 Git 知识库。维护者已在虚拟机及不同模型上验证日常使用，迁移验证不再列为首要任务。下一轮建议减少两种重复劳动：让模型维护本可推导的事实，以及让下一次会话重新猜测上一次已经确定的任务关系。

## 0x01 半年里实际改变了什么

比较主仓 5 月 16 日之前的最后一个提交 `b65b18b` 与当前提交 `ee7664e`，共 `347` 个提交。下表的历史数字以 Git 树为准，安装数字则来自 11 月 16 日当前工作树；不将两种口径混算。

| 观察项 | 可核对的变化 | 对决策的意义 |
| --- | --- | --- |
| 工作区入口 | [AGENTS.md](../../../../AGENTS.md) 从 86 行缩至 27 行，主仓跟踪的技能入口从 6 份增至 9 份 | [4 月方案](../../issues/2026-04-06-skills-first-architecture/README.md)提出的按需加载已经落地，不必再做一次目录重构 |
| 知识积累 | 公开知识目录的 Markdown 从 110 份增至 168 份，issue 和 article 的入口从 32 份增至 57 份。按 Git 路径历史计，252 个提交涉及知识目录 | 这里积累了真实的项目决策和验收材料，值得作为跨会话来源保留。提交量不能证明模型找得到正确版本 |
| 分发与恢复 | 8 月接入项目 Skill，10 月补[跨主机初始化](../../issues/2026-10-11-workspace-portable-bootstrap/README.md)。随后又修正改名残留和上游删除检查，见提交 `0626058`、`23fbf2b` | 安装和更新已经产生持续维护工作，下一步应验证用户拿到的能力，而不只看目录是否存在 |
| 执行与观测 | [聊天桥接器](../../../../apps/agent-chat-bridge/docs/development.md)已经隔离通道与执行器。11 月 15 日提交 `30cb59c` 将 Cursor 逐次用量的采集交给 Trace 插件 | 保留任务入口和执行器边界，用现成遥测解释失败，不在 Bridge 内再造完整观测系统 |

**本次实际检查。** 工作区技能目录有 44 个可读的 `SKILL.md`，其中 12 个通过项目符号链接引入。工作区内的 Claude 和 CodeBuddy 挂载目录各有 32 个，这是[既定挂载策略](../../../../CONTRIBUTING.md)；目录数不能代替客户端实际发现结果，用户级安装也可能补充技能。

本机运行 `make verify-skills` 返回 `0`，同时报告 3 个未声明来源。[校验器](../../../../scripts/verify_skills.py)区分断链和告警，因此绿灯符合其设计，但不能证明另一台机器能重建同一套能力。一个已核对的例子：构建机排障 Skill 的说明仍要求从 Cursor 专属目录找取数依赖，该路径在本机不存在，而工作区技能目录有这份依赖。它说明文档与环境有偏差，不等于整个排障流程已失败。

**评测已有起点**：[7 月加入的方案写作样例](../../../../.agents/skills/knowledge-mgr/evals/evals.json)有 4 题，每题 5 条预期，引用的 13 份输入在本机都存在。其中 2 份依赖安装的外部 Skill，另有一道题的背景仍称库里只有一个样例。此次只核验输入和预期，未运行模型，无法据此推断当前通过率。

## 0x03 业界如何划分模型与工作区的职责

这些材料分别是团队落地经验、可用产品、参考实现和成熟的工程对照，不能合并解读为一次统一的架构迁移。

| 来源 | 实际做法 | 可以借鉴的部分 |
| --- | --- | --- |
| [Stripe 支付方式集成复盘，2026 年 9 月](https://stripe.dev/blog/stripes-payment-method-factory-orchestrating-agents-for-repeated-custom-integrations) | 在重复但各不相同的集成任务中，保留可复用指令，依据执行记录、决策和 PR 评语提出指令改进 | 用户纠正一次，先留下可复现的例子，再决定是改提示、修工具还是补领域知识 |
| [Cursor Agent SDK，2026 年 10 月](https://cursor.com/changelog/agent-sdk) | 对同一个 Agent 分别定义按需过程、带类型的动作、外部连接和验收用例 | 一项能力可以同时需要 Skill 和工具；接口是 CLI、函数还是 MCP，取决于谁来调用 |
| [GitHub Agentic Workflows，2026 年 10 月正式可用](https://github.blog/changelog/2026-10-29-github-agentic-workflows-generally-available/) | Agent 默认只读，拟执行的外部写操作由平台验证后执行 | 分开“写出评审意见”和“获准发布意见”，在实际写入处检查目标与授权 |
| [OpenAI Symphony 工程说明](https://openai.com/index/open-source-codex-orchestration-symphony/) | 团队用 issue tracker 承载工作，每项任务关联隔离工作区，让执行会话可以替换 | 借用任务身份和交接机制即可，不要求引入常驻调度器 |
| [Backstage 目录模型](https://backstage.io/docs/features/software-catalog/life-of-an-entity/) | 从受版本控制的描述和其他权威来源加工出目录视图 | 成熟的非 AI 对照：让每条事实有一个维护位置，按需生成视图；个人多仓工作区不需要因此部署 Backstage |

## 0x04 优先打磨的三个流程与注册示例

**第一项：把知识索引做成可重建的视图。** 半年主仓有 252 个非合并提交涉及公开知识目录，其中 129 个修改了至少一个索引，100 个修改了至少两个，74 个修改了至少三个。提交共改不等于耗时，但足以说明维护频率。上一次写入本报告也是正文一处、索引三处。

先拿本项目的 article 分类试点。标题、摘要和标签取自正文 frontmatter，链接来自路径，数量按对象规则计算；“最近更新”若指实际操作，须取变更记录，不能把文档日期冒充操作日期。手写导读、项目别名、可见性和归档选择仍保留权威来源。

在提交 `ee7664e` 上只读比对两个已有公开文章分类，按目录枚举的 5 篇和 1 篇文章分别与对应索引的链接集合一致。这个小样本支持先试生成，并未发现这两份索引有漏项。公开、私有应分开生成。[现有门户生成器](../../../../apps/knowledge-portal/scripts/generate-vitepress-config.mjs)从索引开始遍历，再生成侧栏与元数据；直接复用其遍历结果无法发现从未被索引的新文章。

验收用新增、改名、归档三个变更：作者只维护事实来源，生成物不丢手写内容，连续运行两次无额外差异，CI 能指出漏更新。先在一个分类跑通，再判断全库改造是否划算。

**第二项：让研发任务带着已有关系跨会话。** [评审 Skill](../../../../.agents/skills/code-review/SKILL.md)遇到已关联 PR 会查已有锚点；首次评审则要从 diff 目录和标识符反推方案。开发阶段通常已经知道当前单据、方案和 PR，等到评审再重建这层关系是可以减少的工作。复用单据里的 PR 回链和 PLAN 里的版本锚点，补齐缺的关系即可。

例如，把单据、可选 PLAN 路径和完整 PR URL 在有权限的内部位置关联起来。接手者用 URL 定位方案，再向 Git 和 CI 读取当前提交及检查结果。允许一个单据关联多个 PR，也允许小改动没有 PLAN；老任务无锚点时再退回内容检索，没有唯一结果就不自动改绑。

公开 PR 不写内部单号。先抽几次已交付任务，检查换会话后能否找到正确方案、正在评审的版本和未解决事项，不先造任务数据库。

**第三项：把重复判断规则改成有证据的维护流程。** 选一个常被人工纠正、又确实需要模型判断的任务。沿用已有评测样例形式，保存脱敏输入、预期证据和不能做出的结论；只在模型、指令或相关工具变化时回放。比如“构建步骤与指标异常重叠”足以列为嫌疑，不能据此认定因果。

该题若败在指标窗口换算就修取数脚本；若数据正确但归因过强就改 Skill；只有在过去的版本上复现、修改后过关，才保留这条规则。事实过期则修知识对象，不自动把聊天全文写成长期记忆。

外部写操作另外处理。评审质量仍由模型判断，发布前校验目标仓库、PR 和授权范围可以由现有写入入口执行。已经有 CLI Guard 的命令优先复用已有检查；涉及 MCP/API 的写入要在对应入口执行约束，不能假设本机 hook 覆盖所有路径。

**仓库注册作为小改动处理。** [registry.py](../../../../.agents/skills/project-mgr/scripts/registry.py)已经提供 `path`、`skills` 和 `sync`，而[项目管理 Skill](../../../../.agents/skills/project-mgr/SKILL.md)还要指导 Agent 探测 Git 信息、选择注册范围、写注册表和知识索引。公共和私有注册表继续保存工作区事实，本机路径覆盖继续留在本机；对既有仓库无需强加一个新的清单文件。

同名冲突如何解释、是否接入、删除时要不要保留知识，属于有上下文的决策。重复探测、校验和生成变更预览可以直接复用现有 Python 模块；只有人、CI 或多个入口都需要调用同一种写操作时，再把它做成稳定子命令。先生成索引，注册流程里的一部分写入便自然消失了。

**暂缓的投资。** 暂不建设覆盖全部 Skill 的统一 CLI、不强制每次修改开单写方案，也不从聊天记录自动生产新规则。只在反复丢失任务关联时推广任务锚点，在多次发现相同纠正时扩充评测，在需要离线继续运行时才比较内网执行器和托管 Agent。

## 0x05 证据边界与复查

历史统计仅覆盖主仓，不含私有仓提交、其他项目提交和聊天次数。知识文件的数量包含索引，issue 和 article 则只数目录下的入口文件，不包含 snippet 和 troubleshooting。本地目录检查与文件存在性检查不等于跨客户端实跑，外部论文结果也不代表本工作区实测收益。

```bash
git rev-list --count b65b18b..ee7664e
git rev-list --count b65b18b..ee7664e -- knowledge
git show b65b18b:AGENTS.md | wc -l
git show ee7664e:AGENTS.md | wc -l
make verify-skills
```
